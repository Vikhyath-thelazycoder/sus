## What was built

| Task | Result |
|---|---|
| T-7.1 Browser parsing | `src/web/upload/parse.ts` uses the same reader, structure parser and chunker as curated ingestion. It runs in a Web Worker (`parse.worker.ts`), and pdf.js runs inside that worker in its "fake worker" mode. The main thread terminates the worker after 60 s, which stops everything. Before pdf.js sees the bytes: the `%PDF-` magic bytes and a 25 MB cap. After: more than 100 pages, more than 1.5 M extracted characters, more than 600 chunks, or no text layer (scanned) → rejected. `enableXfa: false`, no font faces, no system fonts. pdf.js 6.5 never runs PDF JavaScript. The fallback title is the file name **without its path**. |
| T-7.2 `POST /api/uploads` | Three steps, the same as curated ingestion: **create** (metadata + section previews) → **chunks** (≤ 32 per call, the server embeds) → **finish**. Strict zod schemas: no client IDs, owner, vectors or unknown fields. Page numbers are checked against the document. The server picks the paper ID (random), chunk IDs, owner, `created_at` and `expires_at` (+7 days), and computes every embedding. **Atomic quota:** a single `INSERT … SELECT … WHERE count < 5 AND pages + n ≤ 100`, checked by the row count. Expired uploads stop counting. `UPLOADS_ENABLED=false` → 503. Retried batches are upserts. |
| T-7.3 Upload UI | Library → **Add your own PDF**: drag-and-drop or "Choose a PDF"; the limits and **"Don't upload confidential documents to this demo"**; "n of 5 PDFs · n of 100 pages used"; progress **Reading → Splitting → Indexing n of N passages** with a bar; plain-words errors for each failure; "Added … Open it". The paper page has **Delete this upload**. The Library has **Delete my uploads and history**. |
| T-7.4 Owner-only search | Uploads were already in the owner filter (Vectorize `$in ['public', me]`, FTS `owner_id IN`, D1 re-check). New: the D1 re-check (`fetchChunks`) now also drops **expired** uploads, and unfinished ones (`status = 'processing'`) never show. Sources from uploads carry "Your upload · unverified". |
| T-7.5 Cleanup | `src/worker/cron.ts`, a Worker `scheduled` handler running daily at 03:17 UTC. It deletes uploads past 7 days, and unfinished uploads older than 1 hour, then any leftover vectors. **Vector tombstones** (migration 0003): the chunk IDs are written in the same D1 batch that deletes the rows, then removed from Vectorize, then cleared. If Vectorize fails half-way, the cron finishes the job, and search never shows the leftovers in the meantime. `DELETE /api/uploads/:id` and `POST /api/me/delete` ("delete my data": uploads, vectors, chats, messages, usage) use the same path. |

## T-7.6 / T-7.7: scanned PDFs and the chat-box upload (2026-11-06, after the owner's feedback)

**Why the owner's PDF failed:** `1793015628-7d8b946f.pdf` (4 pages, 5.2 MB, made by lightpdf.com) has **no text layer**. Each page is one full-page image (pdf.js: 0 text items, 1 image per page), so "looks like a scan" was correct.

**OCR (T-7.6):**
- **How it works:** pages with fewer than 20 characters of text are drawn to an OffscreenCanvas at ≈ 300 dpi inside the upload Web Worker and read by tesseract.js 7 (English `best_int` model). Everything is self-hosted from `/ocr/`: `scripts/copy-ocr-assets.mjs` copies the files at build time, so there is no CDN, and the CSP only gains `'wasm-unsafe-eval'` (SECURITY.md §3.3).
- **Columns:** tesseract's own lines ran across the gutter of this two-column paper. It now returns **words**, and our existing layout code orders the columns, the same as for text PDFs.
- **Title:** tesseract's page layout skipped the large title. A second, half-size pass in sparse-text mode adds what the first pass missed. Result: title "Design of Intelligent Machine Learning Model for Real Time Prediction of Heart Diseases", 4 pages, 18 passages, about 13 s of OCR.
- **"Ready" means searchable:** right after indexing, Vectorize hadn't applied the vectors yet, so the first questions found nothing. `/finish` now waits, polling every 1.5 s for up to 45 s, until Vectorize's `processedUpToDatetime` passes the finish time. The chip shows "Making it searchable…" meanwhile.
- **Topic guard:** questions about the owner's own upload were declined as off-topic (it's a heart-disease paper). With live uploads, the guard now blocks only hazards and override attempts, and answers still come only from the sources. The answer prompt says uploads can be on any subject.
- **Measured locally (dev resources), asked straight after Ready:**

  - "Which model reached 95.08% accuracy, and on which dataset?" → "Gradient Boosting … UCI Cleveland dataset (303 records, 14 attributes) [1][4]".

## T-7.11 chat-scoped PDFs and T-7.12 "Use the library" switch (2026-11-06)
Owner report that triggered it: a PDF attached in a new chat was ignored, and answers came from an earlier upload. Cause: every question searched all of the owner's uploads, and T-7.9's own-uploads list boosted the older, already-indexed PDF.

- **Data:** migration `0004`: `papers.chat_id` (NULL = curated or personal library) and `chats.use_library` (NULL = default). Upload vectors carry `chat_id` metadata; Vectorize needs a `chat_id` metadata index (dev created 2026-11-06; prod pending).
- **Search scope:** the library (curated + uploads not tied to a chat) and the chat's own PDFs, in keyword search (SQL), Vectorize (two queries, since filters can't OR across fields) and the D1 re-check. The chat list counts twice in RRF.
- **Chat lifecycle:** `POST /api/chats` creates the chat on the first attached PDF (one create even for several PDFs). `DELETE /api/chats/:id?pdfs=delete` deletes the chat's PDFs; without it they move to the library. The app asks each time.
- **Library switch:** saved with the chat when the user changes it; default (proposed, **not yet confirmed by the owner**) is off when the chat has a PDF, on when it has none. Answers with the library off are never cached.
- **Uploads made before this change** have no chat, so they count as personal-library PDFs: used in chats with the library on.
- Tests: worker 134+ (scope per layer: keyword, Vectorize filter, D1 re-check; another owner; deletion both ways; library default and saved choice; no cache with library off); web 37 (switch default and flip, upload sends the chat ID, delete question, library choice sent).
- **Local end-to-end (Node server on dev D1/Vectorize/AI + Groq), 8/8 pass:** upload in chat A, finish without waiting, a question right after Ready in A cites the upload ("87.3 %", 2.8 s); chat B never sees it; library off cites no curated paper, on cites it; GET reports 1 PDF and the saved choice; deleting chat A with its PDFs removes the PDF.
